# 이 프로젝트를 위해 알아야 할 핵심 개념

## 1. HTTP와 REST API

- GET은 조회, POST는 생성, PUT은 전체 수정, DELETE는 삭제에 사용한다.
- 성공 여부는 응답 본문뿐 아니라 200, 201, 400, 401, 403, 404 등의 상태 코드로 표현한다.
- 401은 인증되지 않음, 403은 인증되었지만 권한이 부족함을 뜻한다.
- 입력 DTO에 Bean Validation을 적용해 필수값, 길이, 날짜와 팀 인원 규칙을 API 경계에서 검증한다.

## 2. Spring의 계층과 의존성 주입

Controller가 Repository를 직접 호출하지 않고 Service를 거치는 이유는 업무 규칙과 트랜잭션을 HTTP 처리에서 분리하기 위해서다. 생성자 주입을 사용하면 의존 관계가 명확하고 테스트하기 쉬워진다.

## 3. JPA와 트랜잭션

- 엔티티는 단순 DTO가 아니라 영속성 상태를 가진다.
- 조회에는 `@Transactional(readOnly = true)`, 변경에는 일반 트랜잭션을 사용한다.
- 자식 목록이 있는 경우 연관관계의 주인, cascade, orphan removal, 조회 쿼리 수를 이해해야 한다.
- 목록 API는 page와 size를 이용해 페이지네이션하는 것이 좋다.
- `ddl-auto=update`는 개발에는 편하지만 운영 스키마 변경 이력을 보장하지 않는다. 장기적으로 Flyway나 Liquibase가 적합하다.

## 4. 비밀번호와 JWT

비밀번호는 복호화 가능한 형태가 아니라 BCrypt 같은 단방향 해시로 비교해야 한다. JWT는 암호화된 비밀 상자가 아니라 서명된 데이터이므로 payload에 비밀번호나 개인정보를 넣으면 안 된다. 서명 키가 노출되면 누구나 유효한 토큰을 만들 수 있으므로 코드와 Git에서 분리한다.

## 5. 브라우저 보안

- XSS: 악성 스크립트가 실행되는 문제로 JavaScript가 읽을 수 있는 Access Token에 영향을 준다.
- CSRF: 브라우저가 쿠키를 자동 전송하는 성질을 악용한다. SameSite 쿠키와 CSRF Token이 대응 수단이다.
- CORS: 다른 출처의 JavaScript가 API 응답을 읽는 것을 제한하는 브라우저 정책이며 인증이나 방화벽을 대신하지 않는다.
- HTTPS: 전송 중인 비밀번호와 토큰을 보호한다. 운영 쿠키는 Secure 속성을 사용한다.

## 6. React 상태와 API 처리

- 서버 데이터, 폼 입력, 인증 여부를 서로 다른 상태로 관리한다.
- API 호출을 공통 client에 모으면 토큰 첨부, 오류 파싱, 재발급을 한곳에서 처리할 수 있다.
- 비동기 요청은 로딩·성공·실패 상태를 모두 고려한다.
- 날짜는 저장 형식과 표시 형식을 분리한다. DB는 정확한 날짜를 유지하고 화면에서는 `YYYY.MM`처럼 표현할 수 있다.

## 7. 환경 변수와 설정 분리

DB 비밀번호, JWT 키, 관리자 비밀번호는 소스에 작성하지 않는다. `.env.example`에는 변수 이름과 안전한 예시만 두고 실제 `.env`는 Git에서 제외한다. 개발·테스트·운영 프로필은 로그 수준과 DB 설정처럼 환경별 값을 분리한다.

## 8. Docker와 네트워크

Compose 내부에서는 서비스 이름이 DNS 이름이다. 백엔드는 `db:3306`, Caddy는 `backend:8080`으로 접근한다. `expose`는 내부 통신에 쓰이고 `ports`는 호스트에 실제 공개한다. 현재 DB와 백엔드는 외부에 직접 공개하지 않고 Caddy만 80/443을 공개한다.

## 9. CI/CD와 최소 권한

CI는 코드 상태를 자동 검증하고 CD는 검증된 변경을 운영에 반영한다. 배포 권한은 저장소·브랜치·리전·대상 인스턴스로 좁혀야 한다. OIDC 임시 자격 증명은 장기 키 관리 부담을 줄인다.

## 10. 운영은 실행 이후부터 시작된다

서비스가 한 번 실행되는 것과 안정적으로 운영되는 것은 다르다. 로그, 상태 확인, 백업, 복구, 인증서, 비밀 교체, 의존성 업데이트, 장애 시 롤백까지 준비해야 실제 운영 가능한 서비스가 된다.
